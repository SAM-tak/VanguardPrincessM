# 通常更新の内訳と表示待ちの再開省略

2026-10-15。[0159](0159-rollback-profile.md) の計測をコミットした後、通常更新の内訳を測り、
表示待ちのフレームでコルーチンを再開しない経路を追加した。

## 約2.8msの更新はどこに使われるか

`netprofile.part()` で、通常更新とロールバック再計算を別々に記録する。
同じPCの2プロセス、Release lovec、CPU同士、ラストステージ、5秒ラウンド、受信障害あり。
最適化前のシードは1280802992、2420フレーム。以下はホスト／ゲストの平均ms。

| 更新の区分 | ホスト | ゲスト |
|---|---:|---:|
| 入力・CPU・操作 | 0.459 | 0.460 |
| ラウンド進行・演出 | 0.217 | 0.209 |
| ステージ・揺れ | 0.340 | 0.350 |
| HUD | 0.334 | 0.332 |
| キャラ・オブジェクト全体 | 1.389 | 1.374 |
| ├ スクリプト | 0.826 | 0.813 |
| ├ 判定・接触処理など | 0.251 | 0.256 |
| └ 移動・押し合い | 0.230 | 0.230 |
| 通常の物理更新1フレーム全体 | 2.840 | 2.817 |

子の区分を親に再加算しない。準備・後処理・計測の記録などもあるため、表示した区分だけでは全体に一致しない。
判定より、キャラ・オブジェクト・ステージ・HUD・ラウンドのスクリプト駆動の費用が大きかった。
CPU同士の特定の試合であり、全キャラ・人間操作・全ステージの上限値ではない。

10msの物理フレーム予算に対し、通常更新だけで破綻してはいないが、約4分の1を消費する。
これを4フレーム実行し直すと、再計算だけで約10msになる。描画は別の費用。

## hold の高速経路

従来は `hold()` の表示待ち中も `co.resume()` でコルーチンを再開し、
`waitTimer -= 100` して次の `yield^` に達していた。

`heldSkill` に hold で中断しているコルーチンを記録し、`advance()` で次を確認する。

- 今の `skill` と `heldSkill` が同じコルーチン。
- `waitTimer >= 100` で、100減らしても待ちが終わらない。

この場合はタイマーだけ100減らして、コルーチンのスタックを触らずに戻る。
中断位置と hold のローカルは、通常どおり再開してもう一度中断した場合と同じ。
待ちの終了フレームや、hold 以外の yield では通常の再開に戻る。

ヒットストップは既存の `stepScript()` の分岐が先に処理するので、待ち時間を減らさない。
技開始では記録をクリアする。コルーチン同一性も確認するため、`skill` を直接置き換えても
古いコルーチンの待ちを誤って省略しない。`heldSkill` は `assign^` による保存・復元の対象になる。

## 同じ試合で比較

再現用に `tools/test-lan.ps1 -Seed` と `main.setVSSeed()` を追加した。
通常の試合は従来どおりシードを選ぶ（既定値-1）。

```powershell
./tools/test-lan.ps1 -Impaired -Profile -Stage 7 -Seed 1280802992
```

最適化前後とも、2420フレーム、勝敗0-2、最終体力826／874、全入力の検査値70235634で一致。
両プロセス間の状態照合と、巻き戻しなしの通常リプレイの100フレームごとの照合・終了結果も一致した。

| 平均ms | ホスト：前→後 | ゲスト：前→後 |
|---|---:|---:|
| 通常更新1フレーム | 2.840→2.685 | 2.817→2.673 |
| 再計算1フレーム | 2.723→2.594 | 2.694→2.539 |
| キャラ・オブジェクトのスクリプト | 0.826→0.776 | 0.813→0.775 |
| 補正1回全体 | 14.502→13.909 | 14.419→13.987 |

通常更新は約5%、再計算1フレームも約5%短くなった。通常更新の中央値も
2.584→2.479ms／2.603→2.483msに短縮した。大幅な改善ではなく、補正1回の10ms予算はまだ未達。
固定したのはステージ・シード・入力であり、OSスケジューリングや受信のタイミングは同一にはならない。
各1試合の測定値から、あらゆる場面で5%速いと保証するものではない。

## 比較テストと単体ベンチマーク

- `-Test hold-fastpath`: 毎フレーム記録を消して従来どおり再開させる経路と比較する。
  小数・ゼロ・負の待ち、タイマーの外部変更、ヒットストップ、技変更、コルーチンの直接置換、
  hold以外のyield、スナップショットからの2回復元を検査。
- `-Test bench-hold`: 32体×2000フレームを7回。開始処理を除き、長い表示待ちの `stepScript()` を測る。
  高速経路と hold 内の記録追加を一時的に除去したソースを別プロセスで測り、その後元に戻して測った。
  他のゲームテストを終了してから順に実行した。
- 単体ベンチマークの7回の中央値は4.6643→3.8739µs/actor-step（約17%短縮）。
  表示待ちだけの数字なので、ゲーム更新全体の改善率とは区別する。
- `costate-probe`、`events`、`vm-audit`、`combat-flow`、`snapshot-replay`、`replay-controls` でも回帰確認する。
