# ロールバックの費用を分解する

2026-10-15。補正の平均14〜18msが何に使われているかを計測した。
今回は動作や保存方式の最適化は行わず、計測を追加した。

## 再現方法と計測範囲

```powershell
./tools/test-lan.ps1 -Impaired -Profile -Stage 7
./tools/test-lan.ps1 -Profile -Stage 7
```

`-Profile` は実時間実行（`-Realtime`）も有効にする。ラストステージ、CPU同士、5秒ラウンド。
AMD Ryzen 5 2600、Release lovec、同一PCのホスト・ゲスト2プロセス。
障害ありでは受信に18〜30msの遅延・順序逆転・重複・欠落を加える。
試合中はサンプルを蓄積するだけで、試合後に集計する。通常は計測無効。

- `restore.ms`: 同じオブジェクトへの書き戻しとコルーチン復元。
- `resim.step.ms`: 再計算のゲーム処理1フレーム。保存や描画を含まない。
- `correction.resim.ms`: 補正1回の再計算時間の合計。
- `snapshot.ms`: CPU状態も含めた保存1回。新規作成／再利用、補正中／予測直前を区別する。
- `snapshot.reach/copy/coroutines/rest.ms`: 既存の `snapshot.lastProfile()` による内部の内訳。
- `correction.snapshot.ms`: 補正中の保存時間。保存しなかった補正は0。
- `correction.ms`: 復元から元の現在フレームまでの再計算・保存・付随処理。
  予測外れ（`mismatch`）と、予測が合っていても必要な保存点更新（`rebase`）を分ける。
- `normal.step.ms`: 通常のシミュレーション1フレーム。
- `update.ms`: ネットワーク処理等も含む update コールバック。物理更新は0〜2フレーム。
  補正あり、保存だけあり、いずれもなしの3区分も記録する。
- `draw.ms`: CPU側の描画コールバック。GPU完了、clear、present、vsync待ちは含まない。
- `frame.cpu-update-and-draw.ms`: 同じ描画フレームの update と draw の計測値の和。
  `frame.with-correction/with-snapshot/ordinary.ms` でそのフレームの作業別にも集計する。
- `frame.interval.ms`: update に渡された実際の `dt`。描画待ち・OSスケジューリング・テスト側処理等も含む間隔。

いずれも経過時間で、プロセスのCPU使用時間ではない。別プロセスに実行権を取られた時間やGCも含み得る。
最大値の原因をGCやGPUに断定する計測ではない。サンプル記録にも小さな負荷がある。
パーセンタイルは nearest rank（`ceil(n * p) - 1`）。

100Hzは物理更新の周期で、描画コールバックの周期と同じとは限らない。
`update.frames` を併記しており、描画フレームの総費用をそのまま「物理1フレームの費用」とは扱わない。

2420フレーム、シード1358557099。両側の状態照合と通常リプレイとの照合が成功。

| 計測対象（平均ms） | ホスト | ゲスト |
|---|---:|---:|
| 通常更新1物理フレーム | 2.559 | 2.540 |
| 保存単体・入れ物再利用 | 2.262 | 2.279 |
| 描画コールバック | 5.340 | 5.325 |
| updateコールバック | 3.770 | 4.061 |
| update＋draw | 9.110 | 9.385 |

予測外れは0／1回、保存点更新のための再計算は8／10回。

この測定は実機2台のLAN遅延や処理時間を保証するものではない。
描画1回あたりの物理更新数は平均1.264／1.260フレームだった。

## 補正があった描画フレームを直接集計

作業別に update と同じフレームの draw を合算する計測を追加して、障害ありをもう一度実行した。
2420フレーム、シード2059649559。両側の24回の状態照合、全入力、最終結果と通常リプレイの照合が成功。

| 計測対象（平均ms） | ホスト | ゲスト |
|---|---:|---:|
| 補正全体 | 14.754 | 14.872 |
| 復元 | 1.973 | 2.150 |
| 再計算 | 10.484 | 10.395 |
| 補正中の保存 | 2.223 | 2.254 |
| 保存単体・入れ物再利用 | 2.663 | 2.660 |
| 更新＋描画：補正あり | 25.481 | 25.096 |
| 更新＋描画：保存あり、補正なし | 13.655 | 13.309 |
| 更新＋描画：どちらもなし | 9.112 | 8.812 |

補正ありの描画フレームは319／334回、中央値23.669／23.166ms、p95は41.215／40.538ms。
これもGPU完了やpresent待ちは含まないCPUコールバックの和。
補正1回あたりの再計算は平均3.853／3.835フレームで、補正時間の88.7／88.5%が保存点更新だった。
初回とシード・試合の長さ・進行中の対象数が異なるので、値の差をコードの性能差とは扱わない。

全測定について、復元＋再計算＋保存＋付随処理の合計と補正時間の合計が一致すること、
再計算サンプル数とフレーム数が一致すること、パーセンタイルの順序を集計データから検査した。
計測無効でも通信対戦と通常リプレイの照合が成功することを確認した。

## 読み取れること

14〜18msは保存単体の費用ではない。補正では約4フレームを実行し直しているため、通常更新が
1フレーム約2.5msでも再計算だけで約9.6msになる。保存だけを半分にしても、今回の補正平均の短縮は
約0.9msにとどまる（他の処理時間が変わらない場合）。

保存・復元のコピー削減には余地があるが、保存点更新のための再計算を減らせるかも検討する価値がある。
ただし、古い保存点を単に長く保持すると、入力不一致時の再計算区間が長くなる。
確定状態をどう得るかと、補正1回の上限をどう保つかを含めた設計上の検討が必要。
